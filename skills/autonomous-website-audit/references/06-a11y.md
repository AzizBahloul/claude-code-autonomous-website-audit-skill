# Layer: a11y

> **Answers:** can someone using only a keyboard, a screen reader, zoom or a phone use this page?
> **Gate:** `shots/a11y/SLUG/` holds a capture with axe results and a keyboard probe.

The `design` layer has already fixed what the page looks like. This layer fixes what the page
*means* to assistive technology. Use an installed accessibility skill alongside these steps
when one exists (see setup).

## Steps

1. **Run the automated pass** for the page's main role, in both themes:
   ```bash
   node ${CLAUDE_SKILL_DIR}/scripts/crawl.mjs capture --base http://localhost:3000 \
     --path URL --storage .website-audit/auth/ROLE.json --themes light,dark \
     --viewports desktop,phone --keyboard --out .website-audit/shots/a11y
   ```
   `--keyboard` tabs through the page on non-touch widths and records every focus stop.
2. **Fix every critical and serious axe violation** (below). Fix moderate ones when the fix is
   local to the page.
3. **Fix the keyboard findings:** focus rings, traps, controls that only a mouse can reach.
4. **Check the semantics by reading the code**: landmarks, headings, names, live regions.
5. **Check touch, zoom and motion.**
6. **Re-run step 1** and confirm the counts dropped. Then mark the layer done with the
   before and after counts in the note.

## Reading the axe results

`jq '.a11y[] | {id, impact, nodes, targets, help}' FILE`. The scan runs the WCAG 2.0, 2.1
and 2.2 A and AA rules only, so every finding maps to a success criterion. The most common
findings, and their fixes:

| axe id | Usual fix |
|---|---|
| `color-contrast` | Use a darker token in light mode, or a lighter one in dark mode. Never change the token globally without checking every user of it |
| `label`, `select-name` | A visible `<label for>`, or `aria-label` when the design has no visible label |
| `button-name`, `link-name` | Icon-only controls need `aria-label` (translated) or visually hidden text |
| `image-alt` | Meaningful images describe their content; decorative ones get `alt=""` |
| `html-has-lang`, `valid-lang` | Set `<html lang>` from the active locale, not hard-coded |
| `aria-*` (allowed-attr, required-children...) | Prefer the native element (`<button>`, `<dialog>`, `<details>`) over ARIA on a `<div>` |
| `target-size` | Pad the hit area to 24×24 px or more (44 px is the comfortable size on phones) |
| `nested-interactive` | A link or button inside another one: make the card a single target, or separate them |

Automated rules find perhaps a third of real problems. Steps 3 to 5 find the rest.

## Keyboard and focus

From the report's `keyboard` block:

- **`noIndicator`**: elements whose focused style is identical to their unfocused one. Add a
  visible `:focus-visible` style from the design tokens (an outline or ring with 3:1 contrast).
  Never use `outline: none` without a replacement.
- **`trap`**: focus got stuck cycling inside one element. Allowed only inside an open modal,
  which must close on `Escape` and return focus to the control that opened it.
- **`pointerOnly`**: elements with `cursor: pointer` that the keyboard can't reach, usually
  `<div onClick>`. Replace each with a `<button>` or `<a href>`. Adding a `tabindex` and a key
  handler by hand is the fallback.
- **`offscreenFocus`**: focus lands on something invisible, such as a closed menu's links.
  Hide closed content with `hidden`, `inert` or `display: none`.
- **`skipLink`**: false on a page with a long navigation means keyboard users tab through all
  of it on every page. Add a skip link to the main content in the shared layout.
- **Order:** `stops` should follow the visual order. A positive `tabindex` is almost always wrong.

Then check by hand what the probe can't: open and close every menu, dialog, tab set and combobox
with the keyboard alone (Enter, Space, Escape, arrow keys, following WAI-ARIA APG patterns),
and check that focus moves into dialogs and back out.

## Screen-reader semantics

Read the page's components:

- **Landmarks:** one `<main>`, plus `<nav>`, `<header>` and `<footer>` where they apply.
- **Headings:** one `<h1>` (`structure.h1Count`), with no skipped levels in sections.
- **Names:** every control's accessible name matches its visible label (WCAG 2.5.3).
- **State:** toggles expose `aria-pressed`, `aria-expanded`, `aria-selected` or `aria-checked`.
- **Live updates:** toasts, form errors and async results use `role="status"` or `aria-live`.
  Form errors are linked to their field with `aria-describedby`, and focus moves to the first
  error on submit.
- **Tables:** data tables have `<th scope>`, and layout is never done with tables.
- **Duplicate ids** (`structure.duplicateIds`) break `label for` and `aria-*` references. Fix them.

## Touch, zoom and motion

- **Touch targets:** fix `smallTargets` from the phone captures.
- **Zoom:** the viewport tag must not contain `maximum-scale=1` or `user-scalable=no`. At
  320 px wide (`--viewports 320x700`), the page must reflow without sideways scrolling (WCAG 1.4.10).
- **Motion:** animations longer than a moment respect `prefers-reduced-motion`. Grep for
  keyframes and transitions that have no `@media (prefers-reduced-motion: reduce)` override.
- **Colour alone:** status, errors and chart series also use text, an icon or a pattern.

## Record

Add an "Accessibility" section to the dossier with the axe ids fixed, the keyboard findings
fixed, and anything left open with a reason. Note: `axe serious 5->0, noFocusRing 3->0, pointerOnly 1->0`.

## Mistakes to avoid

- Silencing axe by adding `aria-hidden` or `role="presentation"` to real content.
- Adding `aria-label` that contradicts the visible text.
- Fixing a contrast finding in one theme and breaking the other.
- Wrapping a `<div onClick>` in more ARIA instead of making it a `<button>`.
